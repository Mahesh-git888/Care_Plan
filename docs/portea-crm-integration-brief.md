# Portea Care Plan LP → CRM Integration Brief

**Owner:** Atishay (marketing tech)
**For:** Mahesh + Care Plan engineering
**Status:** MVP live; CRM dual-write ready behind two env vars

## Summary

The Care Plan landing pages (`/`, `/elder-care`, `/dementia`, `/post-discharge`) are live on Vercel and capturing leads today. Every chatbot intake, Call-click and WhatsApp-click is currently appended to a Google Sheet via an Apps Script webhook — that's the MVP source of truth.

The frontend is already wired to **dual-write** every lead to a second destination (the Portea CRM) the moment two env vars are set on Vercel. No frontend code change is required. This doc gives engineering everything needed to provide that endpoint.

## What the LPs already send

Every lead lands at our `POST /api/v1/intake` (or the click-tracking endpoint `POST /api/v1/track`) and is forwarded as JSON. The shape below is what we'll POST to the Portea CRM the moment `PORTEA_CRM_API_URL` is set.

### Headers

```
POST {PORTEA_CRM_API_URL}
Content-Type: application/json
Authorization: Bearer {PORTEA_CRM_API_KEY}    # if PORTEA_CRM_API_KEY is set
X-Portea-Source: portea-care-plan-lp
```

### Expected response

Engineering decides, but the simplest contract that lets the LP report success:

```jsonc
HTTP 200
{
  "ok": true,
  "patient_id": "uuid-assigned-by-crm",      // optional but useful
  "cm_assigned": "Dr. Meera"                 // optional
}
```

Non-2xx is logged and retried-once (best-effort) — it does not block the user's chatbot completion screen.

## Four questions to unblock Phase 1

1. **CRM endpoint URL.** Is there a public HTTPS API today (`https://crm.portea.com/api/v1/leads/intake`?), or do leads need to land somewhere else (S3, internal queue, direct DB) initially?

2. **Auth scheme.** Bearer token in `Authorization` (what the LP currently assumes), API key in a header (`X-API-Key`), OAuth client credentials, IP allowlist, or mTLS?

3. **JSON shape acceptable?** The shape above maps directly to the engineering design doc's `patients` + `intake_sessions` tables. If you want a different shape, share it — we'll map server-side rather than asking the LP to know your schema.

4. **Status writeback.** When a CM marks a lead "called" / "qualified" / "rejected" in the CRM, do we need that status reflected back in the Google Sheet / `/admin/leads` (e.g., via a webhook from the CRM to a `/api/admin/status` endpoint)? If yes, what's the trigger?

## Operational notes

- **PII.** Phone numbers are masked in our logs (only first 2 and last 2 digits visible). They're sent unmasked in the payload to both the Sheet and the CRM since both are first-party destinations.
- **A/B variant.** `ab_variant` is randomly assigned client-side. Don't strip it — the design doc relies on it for the 30-day retention comparison.
- **Click events.** `kind: call_click` / `kind: whatsapp_click` rows have no caller details, just attribution. They tell you which ad drove intent even when the user didn't complete the form. CMs typically don't need to action these directly, but marketing uses them for top-of-funnel analytics.
- **Consent.** Every intake carries `consent_given: true` because we won't accept a submission without the DPDP-compliant checkbox. Reject anything where this is false.
- **Idempotency.** The LP sends one POST per submission with a generated `id`. If the same `id` arrives twice (e.g. due to a retry on our side), please dedupe rather than creating two patient records.

## Files involved on the LP side

- `src/lib/lead-store.ts` — `forwardToPorteaCrm()` does the CRM POST. Same pattern as the Sheet forwarder.
- `src/app/api/v1/intake/route.ts` — receives the chatbot submission, calls `appendLead()`.
- `src/app/api/v1/track/route.ts` — receives Call/WhatsApp click beacons, calls `appendLead()`.
- `.env.example` — `PORTEA_CRM_API_URL` and `PORTEA_CRM_API_KEY` documented.
